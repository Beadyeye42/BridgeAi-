# Bridge-iT security and UI audit — 7 September 2026

Scope: current repository based on audit PR #52 and free-plan PR #54; the 63 API route files were inventoried and screened for authentication boundaries, with focused review of identity resolution, buyer login, billing, quotation writes, webhooks, storage and downloads. Live Supabase configuration and migration statements were checked read-only. No customer messages, payments or production mutations were performed. This is a code/configuration review with local adversarial tests, not an external penetration-test certification or proof of every live journey.

## Live security evidence

- All 59 application tables have RLS enabled and forced. The application role has neither superuser nor BYPASSRLS privileges.
- All three storage buckets are private. The application bucket restricts size and MIME types. Two legacy buckets have no bucket-level size/MIME limits; private status alone does not establish whether their remaining object policies are appropriate. Review/decommission separately without deleting user data blindly.
- The current security advisor reports leaked-password protection disabled. The authenticated Supabase dashboard confirms it is available only on Pro and above; this project is on Free. No paid-plan change was made. [Supabase password security](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
- Performance advisors were inspected. Existing multiple-policy and unused-index notices need representative query measurements; do not delete indexes or weaken policies merely to silence notices.
- Server identity uses Supabase getUser() and verified claims. Administrator authority comes from the active platform-administrator row; supplier authority from active company memberships. No general new trustedPrisma bypass was introduced.
- Customer-value encryption uses AES-256-GCM with random nonces and blind indexes. This confirms the reviewed implementation, not deployment key custody, key rotation or backup recovery.
- Webhooks validate provider signatures. Verified Stripe processing fetches current provider subscription state. Concurrent event handling and external-provider replay remain live integration test targets.

## Unresolved risks and verification limits

1. Prepared fixes are not production protection until deployed with their migrations. Pricing PR #53 is incompatible with PR #54; do not apply both free-plan migrations.
2. Automatic general PDF/supplier-evidence scanning is not operationally verified. Pending assets remain blocked; a scanner/worker must be configured before promising completed document processing. The missing direct company-ownership path in evidence downloads was fixed and tested: clean own-company evidence is permitted, other-company and unscanned evidence are denied.
3. Quote recovery is scheduled once daily. Normal request-triggered processing is faster, but crash recovery can still be delayed. Define an acceptable queue age and provision an appropriate scheduler.
4. Content Security Policy still allows inline scripts. A nonce-based policy would provide stronger XSS defence; introducing it needs complete authentication/billing/browser testing. No exploitable XSS was demonstrated here.
5. Upload routes parse multipart bodies before checking File.size. Hosting request limits offer a separate bound; streaming limits should be added if hosting or allowed sizes change. Storage success followed by quotation metadata failure can also leave an orphan object.
6. Authenticated production mobile flows, scanner behaviour, Stripe sandbox upgrades, real WhatsApp delivery, MFA enforcement and backup restore have not been verified end-to-end. No claim of exhaustive security is made.

## Validation

Application regression tests, lint, typecheck, Prisma validation, production build and dependency audit are required before publishing. The current local suite contains 598 passing tests across 70 files. The SQL suite passes in a rollback transaction, including notification atomicity, login limits, tenant denial and existing auth/storage invariants. A separate 20-client concurrency test checks network/customer limits and audit counts.

Public/demo browser checks use test-only configuration and clearly marked sample data. Desktop and 390px mobile homepage checks show meaningful content and no error overlay or horizontal overflow; registration and dashboard are checked separately. These are UI checks, not live signup or payment tests.
